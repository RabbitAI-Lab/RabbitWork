# 功能规格模板

> 每份功能规格必须复制本模板起草，保持固定结构（评审与走查按章节定位）。
> 文件名：`docs/sprint-{N}-{theme}/{MODULE}-NNN-{slug}.md`（编号与分支/测试文件/migration 一一对应）。

````markdown
# {功能名}

| 元信息项   | 内容 |
| ---------- | ---- |
| 文档编号   | {MODULE}-NNN |
| 所属迭代   | sprint-{N}-{theme} |
| 优先级     | P0/P1/P2/… |
| 所属模块   | {module} |
| 文档状态   | Draft / Approved / Prototyped / Implemented / Verified |
| 最后更新日期 | YYYY-MM-DD |
| 上游依赖   | （必须与 dependency-graph.md 一致） |
| 下游消费   | （哪些后续功能依赖本功能） |
| 上游依据   | 需求文档 §x（产品定位确定后） |
| 基线核对   | （对标产品/上代实践的对照章节，如有） |
| 关联架构文档 | api-conventions / rbac-permission-model / … |
| **高保真确认** | **待确认**（确认人 / 确认日期 / 原型链接 `docs/design/{MODULE}-NNN-{slug}/`；UI 类必填，未确认不得编码——AGENTS.md 门禁 2） |
| 工作量估算 | 后端 x 人日 / 前端 y 人日 / 联调 z 人日 |

## 1. 概述
   1.1 功能定位（为什么需要、在系统中的位置）
   1.2 范围边界表（本迭代 ✅ / 后续迭代 ❌ 及去向编号）
   1.3 前置依赖表（依赖文档 + 阻塞原因）
   1.4 **能力表**（每行一条可验收能力：编号/名称/交互类型——rules/testing §1.2 的最小覆盖单位）
   1.5 基线核对（对标基线逐条对照：完全复刻 / 简化实现 / 超出基线；如有）
## 2. 业务逻辑
   状态机 / 流程图（mermaid）/ 规则明细 / 边界与异常
## 3. UI/UX 设计
   页面结构 / 交互细节 / 空态与权限态 / 对话式用例走查
   ——界面类规格必须附 docs/design/ 高保真原型链接，人工确认后方可进入编码
## 4. 技术架构
   数据模型（Prisma schema 级，遵循一次建齐）/ API 契约（方法·路径·请求·响应，zod 定义）/
   前端组件与状态 / worker 侧（如涉及）/ 权限点（packages/shared/permissions.ts 登记）
## 5. 测试用例
   功能用例表（前置/步骤/预期，编号与测试文件一致）+
   JMeter 接口用例清单（四类场景×四项断言，映射 tests/api/{MODULE}-NNN-*.jmx）+
   Playwright UI 用例清单（每条含 UI 断言 + Console 断言 + 接口断言三类，映射 tests/e2e/）+
   关键状态二态覆盖清单（预置/自定义、只读/可写、启用/禁用、空态/有数据、有权/无权——或显式豁免+理由）+
   性能与安全注意
## 6. 基线深度对标（如有）
   对标实现方式 ↔ 本项目实现方式对照表 + 差异化决策及理由
## 7. 里程碑与验收
   交付清单 / DoD（前置：高保真已人工确认）/ 演示脚本 / 回归范围
   ——Sprint 收尾：commit + push 远程，GitHub Actions 远端 CI 全绿（rules/git-workflow.md §8）
````

**元信息表硬性要求**：`上游依赖` 必须与 `dependency-graph.md` 一致；`高保真确认` 字段必须如实（原型文件创建前不得写「原型已产出」——虚标即规格缺陷）；`工作量估算` 按后端/前端/联调分列。

**状态流转**（AGENTS.md §3）：`Draft → Approved（规格评审通过）→ Prototyped（高保真已确认，编码可开始）→ Implemented（代码合并）→ Verified（验收通过）`；状态记录在元信息表，sprint-overview 交付表同步更新。
